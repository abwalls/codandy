## Change 1 — The contract suite was red

`pnpm test:contracts` was failing before this session. Your final checkpoint said "Final
combined checks and browser QA are next," and those checks never ran, so the M2 slice
shipped with a broken suite.

**Symptom.** `UnicodeEncodeError: 'charmap' codec can't encode character '\u2192'`.

**Mechanism.** `backend/app/reporting.py` titles module-dependency report items with a
non-ASCII arrow:

```python
flows.append(item("module_dependency", f"{by_id[source].path} → {by_id[target].path}", ...
```

`tests/analysis-api.test.mjs` spawns Python to generate a real atlas fixture and reads it
from stdout. On Windows, Python encodes stdout with the ANSI codepage (cp1252), which has
no `→`, so the child died and the fixture never arrived.

**Fix — and why it is where it is.** The obvious fix is to change `→` to `->`. That was
rejected: it treats the symptom. *Any* repository path or identifier can be non-ASCII (a
repo with CJK filenames, a symbol named `café`), so the same crash would return the first
time someone analyzed such a repo. The defect is that the test harness could not carry
UTF-8. Fixed at the pipe:

```javascript
env: { ...process.env, PYTHONIOENCODING: "utf-8" },
```

This covers stdout *and* stderr, which matters because the assertion prints
`generated.stderr` on failure — a traceback containing a non-ASCII path would otherwise
crash the error path too.

Locked with a regression assertion so a future "tidy-up" of the arrow does not silently
remove the only coverage of this pipe:

```javascript
// Guards the UTF-8 stdout pipe above: this title carries a non-ASCII arrow.
assert.match(fixture.report.flows.items[0].title, /\u2192/);
```

**Keep the arrow.** It is legitimate user-facing typography and it is now load-bearing
as test coverage.

## Change 2 — Language coverage: 3 extensions to 10

`ARCHITECTURE.md` promised "generic Tree-sitter parsing first" and the product promises to
analyze *any* repository, but `analyzer.py` registered exactly three parsers: `.cs`, `.ts`,
`.tsx`. Everything else was inventory-only.

### The registry

Parsers now come from a suffix table and **load lazily**, so a Python-only repo never
initializes the C# grammar:

```python
LANGUAGES = {
    ".cs": ("C#", ...),          ".ts":  ("TypeScript", ...),  ".tsx": ("TypeScript", ...),
    ".js": ("JavaScript", ...),  ".jsx": ("JavaScript", ...),  ".mjs": ("JavaScript", ...),
    ".cjs": ("JavaScript", ...), ".py":  ("Python", ...),       ".pyi": ("Python", ...),
    ".go": ("Go", ...),
}
```

Everything downstream keys off the **language label**, not the suffix. The old code had
suffix checks scattered through the walk (`if suffix in {".ts", ".tsx"}`); those are now
`if language in {"TypeScript", "JavaScript"}`. Follow that pattern when adding a language —
otherwise new languages silently miss the risk rules.

### Per-language specifics, and the shapes that differ

Node-type names mostly do not collide between grammars, so `DECLARATIONS` is one merged
map. Three cases needed real handling:

- **Go `type_spec`** names structs, interfaces, and aliases with a single node type. The
  kind is resolved from the *body* child (`struct_type` → class, `interface_type` →
  interface, otherwise type).
- **Python `function_definition`** is used for both free functions and methods. A
  `node_kinds` dict tracks each emitted node's kind so a `function` whose parent is a
  `class` is reclassified as `method`.
- **Python decorator routes.** Flask/FastAPI register on the decorator, so the handler name
  lives on the definition *below* the call, not in the call arguments. A pre-scan maps each
  decorator call's `start_byte` to the decorated function's name, and the main walk uses it
  to emit a `pending_handlers` entry. This is why `@app.get("/items")` correctly links to
  `list_items`.

Import source text lives in different fields per grammar, resolved first-hit-wins:

```python
IMPORT_SOURCE_FIELDS = {
    "import_statement": ("source", "name"),   # TS/JS use source; Python uses name
    "import_from_statement": ("module_name",),
    "import_spec": ("path",),                 # Go
    "using_directive": ("source",),           # C#
}
```

Python `aliased_import` (`import os.path as p`) is unwrapped to its `name` field, because
the raw text `os.path as p` fails the import-name regex and would be dropped.

### Routes

`ROUTE_VERBS` gained Go/gin-style uppercase receivers (`GET`, `POST`, …) and three
method-agnostic registrations mapped to **`ANY`**: `route` (Flask), `HandleFunc` and
`Handle` (Go `net/http`). `ANY` is deliberate — those APIs do not state a verb in source,
and inventing `GET` would be fabrication. This is documented in the atlas limitations.

`STRING_TYPES` gained Go's `interpreted_string_literal` and `raw_string_literal`, and the
literal strip now includes a backtick for Go raw strings.

**Known false-positive class, accepted:** `client.get("/items")` in a Python test file
produces a route candidate, same as `axios.get("/api/x")` already did for TypeScript. The
existing guard is the `/`-prefix regex plus 65% confidence and "candidate" wording. This is
pre-existing behavior, not a regression. Do not add a test-file exclusion heuristic without
asking — it would change C#/TS behavior too.

### Manifests

Added `pyproject.toml` (PEP 621 `project.dependencies`, `optional-dependencies`, and
`tool.poetry.dependencies`), `requirements.txt`, and `go.mod`. TOML is parsed with stdlib
`tomllib` — no new dependency and no code execution.

**Only distribution names are extracted, never versions, markers, extras, or URLs.**
`python_requirements()` regex-matches the leading name and discards the rest. Requirement
options (`-r`, `-e`, `--hash`) and comments are filtered before it is called. Keep this
property: version strings and VCS URLs are exactly the kind of content that should not
land in a report.

Framework detection added: Express, Vue, Angular, Svelte (npm); FastAPI, Django, Flask,
Pydantic (Python); Gin, Echo, Chi (Go).

### Local import resolution

Previously TypeScript-only. Now, all still gated on the **unique-candidate rule** (ambiguous
resolution stays `unresolved` rather than guessing):

- **JS/TS** — relative specifiers across `.ts .tsx .js .jsx .mjs .cjs` plus `index.*`, and
  the existing `.js` → `.ts` emitted-extension fallback.
- **Python** — relative imports with correct dot-level semantics (one dot = this directory),
  plus repository-rooted absolute modules; candidates are `.py`, `.pyi`, `/__init__.py`.
- **Go** — import paths are matched against the `module` line from the nearest enclosing
  `go.mod` and resolved to a **directory node**, because a Go package is a directory, not a
  file. This is the only `RESOLVES_TO` edge that targets a directory; `reporting.py` handles
  it fine since it only reads `.path`.

Project association was rewritten to be driven by `LANGUAGE_MANIFESTS` instead of hardcoded
suffix branches. This also fixed a small pre-existing inconsistency: manifest *detection*
accepted `.csproj`/`.fsproj`/`.vbproj` but the association filter only matched `.csproj`.

### The latent bug this uncovered

While mapping node types I found that **TypeScript and JavaScript class members are
`method_definition`**, which was absent from `DECLARATIONS` (it had `method_declaration`, a
C# node type). Consequence: *no TypeScript or JavaScript class method had ever been
indexed.* For a service class or any OO TypeScript codebase, every method was invisible and
the symbol count was silently wrong.

Confirmed against the real analyzer before fixing:

```
class Svc { doWork() { return 1; } helper() {} }
function free() {}
→ before: symbols: 2  (Svc, free)
→ after:  symbols: 4  (Svc, doWork, helper, free)
```

The live smoke repo (`microsoft/TypeScript-React-Starter`) went from **77 to 133
relationships** after the fix. If you see relationship counts in older progress entries
that disagree with current runs, this is why.

## Change 3 — The source viewer

`PLAN.md` M2 called for a "source viewer with stable symbol IDs and line evidence." Before
this, selecting a node showed `path:lines — reason` as text, never the actual code.

### The design constraint, and the call made

The cloned workspace is destroyed before a report is ever viewable — `clone_repository` is
a context manager and `JobStore.run` stores the result *after* the `with` block exits. So
there is no source on disk at view time. Two options:

1. **Embed source in `atlas.json`.** Self-contained and matches "atlas.json is the source of
   truth," but bloats a downloadable artifact enormously and ships every byte whether or not
   it is opened.
2. **Capture during analysis, serve on demand.** Keeps the atlas lean and transfers only
   what is viewed.

**Option 2 was chosen.** `atlas.json` stays a graph document and still carries **no source
bodies** — there is a test asserting this. Source text is captured by the *parent* process
inside the `with` block (the spawned analyzer's protocol was untouched) and held in memory
alongside the report.

Trade-off, stated plainly: a downloaded `atlas.json` has the graph but no code, and the
viewer needs the live service. That is consistent with the app already depending on the
backend to view a report at all (reports are in-memory and expire on restart).

### Security properties — preserve these

`backend/app/sources.py` `collect_sources()` returns `dict[path, SourceFile]`, and
`GET /analyses/{id}/source?path=...` is a **map lookup with no request-time disk access
whatsoever**. That is the core safety property:

- Only paths the analyzer already indexed as **file nodes** are eligible, so secret-matched
  paths (`SECRET_NAME`) and excluded directories (`.git`, `node_modules`, …) are
  unreachable — they were never nodes.
- Traversal is impossible by construction. `../../../etc/passwd`, `/etc/passwd`,
  `C:/Windows/win.ini`, and `.git/HEAD` all return 404 because they are not keys. There is
  a test covering each.
- `SECRET_NAME` is re-applied and `_inside()` validates resolved paths as defense in depth,
  even though nothing should reach them.
- Binary files (NUL byte) are skipped. The TypeScript smoke repo omits exactly one file:
  `public/favicon.ico`.

Budgets are in `Settings`: `max_viewer_file_bytes` (128 KB) and `max_viewer_total_bytes`
(4 MB) per report. Files carrying line evidence are captured **first**, then remaining files
fill the budget, so a large README cannot starve the code you actually need. Truncation
always lands on a line boundary because the viewer indexes by line number. Omissions are
surfaced honestly as an atlas limitation, not hidden.

Retained text is evicted with its report — added to the eviction path in `JobStore.create`
alongside `self.results`. **If you add another eviction path, evict `self.sources` too.**

### Frontend

`components/source-view.tsx` renders line numbers, dims context lines, highlights the
evidence range, and offers a whole-file toggle (capped at 2000 rendered rows; the evidence
window is capped at 240).

Two details that are load-bearing:

- **Lines are split on `/\r?\n/`.** Capture is byte-verbatim, so CRLF files stay CRLF. A
  plain `split("\n")` leaves a stray `\r` on every row. This was found by a test whose
  fixture was written with `write_text` on Windows.
- **Repository text is rendered as text children only, never markup.** It is untrusted
  input. Do not switch to `dangerouslySetInnerHTML` for syntax highlighting without an
  escaping step — and note the analyzer has a rule that flags exactly that pattern.

`SourceView` is mounted with `key={selected.path}` so it remounts per path and its opening
state is *derived* rather than assigned inside an effect. This satisfies
`react-hooks/set-state-in-effect`; if you refactor it, keep the derived-initial-state shape
or ESLint will fail.

The hosted proxy (`app/api/analyses/[[...path]]/route.ts`) has a strict path allowlist that
needed `source` added, and it forwards **only** the validated `path` query parameter, never
the caller's whole query string. A contract test asserts that a `&token=leak` parameter is
dropped.

## Bug fix 1 — Clone-time race in `check_workspace`

**Pre-existing.** Live analysis was failing intermittently with the generic
`"Analysis failed. Check Git availability and local workspace access."`

`_run()` polls `check_workspace(root, limits)` every 50 ms *while git is still running*, to
enforce disk limits during the clone. `check_workspace` walks the tree and calls `.stat()`
on every file. Git constantly creates and deletes lock and temporary files
(`.git/HEAD.lock`, `index.lock`, pack temporaries). When a file was listed by `os.walk` and
deleted before `.stat()` ran, the result was:

```
FileNotFoundError: [WinError 2] ... 'repository\.git\HEAD.lock'
```

The fix tolerates concurrent deletion without weakening the limits — a vanished file simply
cannot contribute bytes, and surviving files are still counted and still trip the limit:

```python
try:
    size = (Path(directory) / name).stat().st_size
except OSError:
    continue
count += 1
total += size
```

`os.walk` already ignores directory errors by default, and `is_symlink()`/`is_junction()`
return `False` for missing paths, so `.stat()` was the only raising call.

This is the kind of flake that wastes hours because the error message points at git
availability, which is fine. Regression test:
`test_workspace_tolerates_files_removed_mid_walk`.

## Bug fix 2 — `tree-sitter` 0.26.0 corrupts memory

**This is the important one.** It affected your C#/TypeScript code too and was only hidden
by small test repositories.

### What happened

Analyzing `pallets/itsdangerous` through the UI produced
`"Static analysis worker exited unexpectedly"`. Direct reproduction gave **exit 139,
segmentation fault**.

### Narrowing it down

The path matters, because several plausible theories were wrong:

1. Clone worked; git was fine. Crash was downstream.
2. `faulthandler` showed *"Windows fatal exception: access violation"* during
   *Garbage-collecting*, and **the reported crash line moved between runs** (once inside
   `pydantic.model_dump`, once inside the node walk). A moving crash site means memory
   corruption, not a logic error.
3. Every file parsed fine **individually**.
4. Not a grammar ABI mismatch — all grammars report ABI 15.
5. Not GC: crashed identically with `gc.disable()`.
6. Not the decorator pre-scan, not parser caching, not tree lifetime — all four variants
   crashed at the same ~45% rate.
7. Renaming `.py` → `.txt` so no grammar ran: **0/14 crashes**. So tree-sitter was required.
8. A script with **no analyzer code at all** — just parse and walk — crashed **14/14**.
   That removed the analyzer from suspicion entirely.
9. Bisecting the walk operations: `child_by_field_name` 0/10,
   `children_by_field_name` 0/10, `start_point`/`end_point` **10/10**.
10. One 404-line file reproduced it **8/8**, deterministically.

### The bug

Reading a node's `start_point`/`end_point` and then its `named_children` corrupts process
memory. `tree-sitter` 0.25.0, 0.25.1, and 0.25.2 are all clean; **0.26.0 is broken**.

The analyzer does exactly this for **every declaration**:

```python
lines = f"{syntax.start_point.row + 1}-{syntax.end_point.row + 1}"
...
stack.extend((child, parent) for child in reversed(syntax.named_children))
```

`pyproject.toml` previously allowed `tree-sitter>=0.25,<0.27`, so 0.26.0 was installed.
Adding Python coverage did not create this bug — it made the product reach trees that
trigger it. **Any sufficiently complex C# or TypeScript repository could already segfault.**

### The fix

```toml
# Upper bound is deliberate. tree-sitter 0.26.0 corrupts memory when a node
# walk reads start_point/end_point and then named_children, segfaulting the
# analyzer process on ordinary sources. Re-verify with tests/test_grammars.py
# before raising this bound.
"tree-sitter>=0.25,<0.26",
```

Plus `backend/tests/test_grammars.py`, which asserts the installed core stays in the
verified series and walks every registered grammar in the exact access order that trips the
broken release.

**Do not widen that bound to pick up a newer release without re-running the analyzer
against a real multi-file repository.** A synthetic fixture does *not* reproduce the bug —
that was tried, and it passed while real sources crashed 100%. The `VERIFIED_CORE` set in
`test_grammars.py` is the gate; the test message says what to do.

### Silver lining

The disposable-process boundary you built worked exactly as designed. A native segfault
took down the spawned worker, and the API survived and reported a dead worker instead of
crashing. That architecture is worth keeping.

## Do not undo these

Five things that look like cleanup opportunities and are not:

1. **The `→` in `reporting.py`** — now load-bearing test coverage for the UTF-8 pipe.
2. **`PYTHONIOENCODING=utf-8` in the contract test** — without it, any non-ASCII repository
   content breaks the suite.
3. **`tree-sitter<0.26`** — see above. Raising it reintroduces segfaults.
4. **`PlaceholderSection` and the two separate report UIs** — explicit user decision.
5. **`key={selected.path}` on `SourceView`** — removing it forces `setState` back into the
   effect and fails ESLint.

Also preserve: `atlas.json` carrying no source bodies (tested), and the source endpoint
doing no request-time disk access.
